Architecture ​

Ports-and-adapters over a flat crates/ workspace. arca-core is pure domain — arca:// refs, the redacting Secret newtype, the env axis, actor attribution — with no I/O. Ports are traits (arca-config, arca-vault, arca-deploy); impls live in separate crates; crates/arca-cli (package arca) is the composition root that wires impls to verbs.

Design rules:

  • No unsafe, no async — the binary stays dependency-light and synchronous; vault impls that speak HTTP use a blocking client (ureq), so no runtime embeds anywhere.
  • Secret never exposes plaintext — no Display/Debug of the value; .expose() is the only way out, called at edges only (child env injection, arca env exports, get).
  • Stores hold ciphertext only — every vault impl encrypts client-side with age (ADR-0001); a remote vault is ciphertext over the wire and at rest, never a plaintext service.
  • Ports are conformance-tested — arca-testkit runs the same contract suite against every vault impl (arca-vault-age, arca-vault-cf): upsert/rotate/list/env-isolation semantics can't drift per backend.
  • One ops shell — arca-ops owns config load, env→vault routing, the env-pin rule, and audit emission; the CLI and the TUI are both thin front-ends over it and cannot diverge.

Front-ends ​

  • arca (CLI) — clap verbs + --json/manifest/schema for machines; the agent interface.
  • arca ui (TUI) — a read-only ratatui browser over the same ops; feature-gated (--no-default-features for a lean binary).
  • arca serve — ndjson IPC over the Vault port with an exec-driven [serve.pdp] policy-decision hook (ADR-0003); peregrin's embedding point.

Boundary — secret materialization only ​

arca owns refs, vaults, env injection, redaction, and the audit wire. Neighbors own theirs — see boundaries for the full map.
